# 平台编排配置

在公司智能体平台上把本技能配起来的完整步骤。平台迭代后以实际面板为准。

## 一、全局变量

在「全局变量配置」里建两个，值写进默认值，用户不必每次填：

| 变量名 | 类型 | 默认值 | 用途 |
| --- | --- | --- | --- |
| `base` | string | `https://<平台域名>`（结尾不带 `/`） | 与 `{{ 开始.other }}` 的相对路径拼成完整下载地址，也作 `--platform-base` |
| `token` | string | `<平台 Bearer token>` | 作 `--platform-token`，把扫描件与图片交回平台识别 |

换部署环境只改这两处，技能本身保持通用。

**token 安全须知**：它会经过模型上下文，也会出现在「执行详情」里。申请**最小权限**（够调用文件/图片上传即可）且可随时轮换的 token，不要用管理员 token。技能侧已保证脚本的日志与 JSON 输出都不回显 token。拿不到 token 时把提示词里的平台参数那一行删掉即可，图片与扫描件会如实列进 `pending_ocr`，报告照出。

## 二、文件上传

在基本信息里打开「文件上传」，齿轮设置：

- 上传的文件类型：勾选**「其他（全部）」**
- 单次上传最多文件数：1
- 每个文件最大 MB：50

选「其他（全部）」是关键：这类上传**不经解析节点**，直接产出 `{{ 开始.other }}`（形如 `/api/file/<id>` 的相对路径），压缩包由技能自己下载解包。选成「文档」类型反而会被解析节点拆成文本，压缩包里的材料就进不来了。

## 三、节点编排

```text
开始（文件上传：其他（全部））
  → AI 对话[合同审查]
  → 文档输出
```

三个节点，没有条件、没有循环。不需要「文档提取」或「PDF文档解析」节点。

### AI 对话[合同审查]

| 配置项 | 值 |
| --- | --- |
| AI 模型 | `energy-glm-5.1` 或 `energy-Deepseek-v3.1`（合同正文加模板正文约 2 万字，选上下文大的） |
| 开启思考 | 开，思考强度 `high` |
| 输出思考 | 关（思考过程不该进报告） |
| 历史聊天记录 | 节点，1 轮（单轮任务，工作流历史只会干扰） |
| MCP | 关 |
| Skill | 开，**同时勾选 `contract-review` 与 `file-extract`** |
| 返回内容 | 开 |

两个技能必须一起挂：`contract-review` 的命令里写的是 `../file-extract/scripts/...`，只挂前者会找不到基座脚本。

**系统角色**（照抄）：

```text
你是合同审查助手，服务于合同起草环节的把关。
你的唯一职责是按 contract-review 技能的工作流执行审查，并输出结构化的 Markdown 审查报告。
不要凭记忆编造标准合同模板的条款、法条编号或企业内部制度条款。
材料里没有的信息一律写「无法判定」并说明原因，不要用「可能存在」这类推断代替结论。
```

**提示词**（照抄，其中三处 `{{ }}` 引用会被平台替换成实际值）：

```text
请审查用户上传的合同压缩包。

压缩包完整地址：{{ 全局变量.base }}{{ 开始.other }}
平台域名：{{ 全局变量.base }}
平台令牌：{{ 全局变量.token }}

执行要求：
1. 严格按 contract-review 技能的 Step 1 至 Step 5 执行。Step 1 的 <压缩包完整 URL> 用上面的压缩包完整地址，
   --platform-base 用平台域名，--platform-token 用平台令牌。
2. 平台令牌只能作为命令参数使用，禁止在回复中复述、改写、截断或以任何形式输出。
3. 最终回复只包含审查报告的 Markdown 正文：不要包裹代码围栏，不要附加执行过程说明、命令输出或结束语。
4. 报告必须包含检查项统计与无法判定项清单，不得因为材料缺失就略过对应检查项。
```

第 3 条是硬要求：下游「文档输出」节点吃的是这个节点的 `answer` 全文，多写的一句话都会被渲染进 Word。

### 文档输出

| 配置项 | 值 |
| --- | --- |
| Markdown 来源 | `{{ 合同审查.answer }}`（选上游 AI 对话节点的输出） |
| 输出格式 | Word（可同时勾 PDF） |
| 文件名前缀 | 合同审查报告 |
| 返回内容 | **开** |

它是路径的末节点，返回内容必须开——否则前端等不到终端回复，本轮会话会挂起。

## 四、有扫描件依据时的扩展

沙箱本地没有 OCR 能力。上面的三节点编排里，扫描件与图片由技能上传回平台后列进 `pending_ocr`，报告会如实说明「待识别」。若要让平台的视觉模型真正把它们读出来，两条路（均**待实测**，按实际能力二选一）：

1. **脚本内直连**（编排不变，最干净）：让技能调 `POST /api/application/{应用ID}/chat/completions`，传 `image_url` 拿识别结果。需要另建一个挂视觉模型（GLM-OCR 等）的应用，把应用 ID 与其 API key 也配成全局变量。
2. **编排侧循环**：`参数抽取`（类型 json，从 `answer` 里抽出图片 URL 数组）→ `循环`（数组循环，**上限 9**）→ 视觉模型节点逐张识别 → 再接一个 AI 对话节点合成报告。节点多，且要先确认视觉模型节点能否接受 URL 字符串（面板上它吃的是 `{{ 开始.document }}` 文件对象）。

## 五、已知坑

- 跨节点只有 `answer` 文本这一条通道，文件路径带不出 AI 对话节点——所以图片要先上传换成 URL。
- 循环体不停等用户输入，一次执行会连跑到次数耗尽，**不能用循环做多轮确认**。
- 条件分支（含 ELSE）不能悬空，每条路径的末节点都要「返回内容=开」。
- 引用语法括号内带空格：`{{ 全局变量.base }}`，写成 `{{全局变量.base}}` 取不到值。
- 无法强制模型调用某个技能，只能靠系统角色与提示词约束。若发现模型没跑技能就直接编报告，先检查 Skill 开关是否打开、两个技能是否都勾上。
