# 报告格式

## Markdown 语法约束

下游是平台「文档输出」节点的 Markdown → Word 渲染，语法超出下面的范围会在 Word 里错版：

- 只用标准 GFM 表格，每列内容尽量短；表格单元格内不要换行、不要嵌套表格
- 标题层级不超过三级（`#` / `##` / `###`）
- 不用 HTML 标签、脚注、任务列表、折叠块
- 不要用代码围栏包裹整篇报告，也不要在正文里用围栏放合同原文——引用原文用行内引号
- 长原文片段截取到能定位即可（一般 30 字以内），不整段复制合同

## 报告结构

固定六节，顺序不变。没有内容的小节写「本次审查未发现」，不要整节删掉。

```markdown
# 合同审查报告

## 一、审查结论概览

一段话结论 + 一张统计表（必须修改 / 建议修改 / 提示关注 各多少条），并写明本次审查所依据的材料：
合同正文文件名、签约依据文件名清单、比对用的标准模板名称。

| 项目 | 内容 |
| --- | --- |
| 合同名称 | ... |
| 合同类型 | 采购 / 施工 / 租赁 / 技术服务 |
| 合同金额 | ... |
| 必须修改 | N 条 |
| 建议修改 | N 条 |
| 提示关注 | N 条 |

## 二、基础文本问题

| 级别 | 位置 | 原文 | 问题 | 修改建议 |
| --- | --- | --- | --- | --- |
| 必须修改 | 第三条 合同价款 | 「大写：壹拾万元整（￥120,000.00）」 | 大小写金额不一致 | 核对实际金额后统一为同一数值 |

## 三、排版格式核对

先用一句话声明本次的可核对范围，再列差异。范围声明直接由 `styles.py` 的 `not_comparable` 转述，例如「合同为 PDF，可核对正文字体、字号、行距、页面尺寸与左/上边距；首行缩进、对齐、右/下边距无法从 PDF 取得，未做核对」。**这句话不能省**——省了就等于让用户把「没报问题」当成「排版没问题」。

| 级别 | 核对项 | 模板要求 | 合同现状 | 说明 |
| --- | --- | --- | --- | --- |
| 提示关注 | 正文字号 | 10.5 磅 | 12 磅 | 全文正文字号大于模板 |

只列 `diffs` 里 `match` 为 `false` 的项；带 `note` 的项要把容差与口径写进「说明」列，并按「提示关注」分级。条款序号断号（`articles.gaps`）也列在本节。

## 四、条款缺失与模板差异

分「模板有而合同无」「合同有而模板无」「实质改写」三小节，每小节一张表：条款名称、模板要求、合同现状、影响与建议。

## 五、风险合规提示

按条款分组，每条写清风险点、可能后果、建议表述方向。仅依据通用合同法律常识，不引用未提供的法条编号或企业内部制度条款。

## 六、材料完整性说明

- 已解析材料：逐个列出文件名与类型
- 未能解析的材料：逐条列出文件名与原因（直接引用 extract.py 的 errors）
- 待识别的材料：逐条列出 pending_ocr 的文件名；已上传待识别与连上传都没成的要分开写
- 由 OCR 或平台解析得到的材料：列出文件名，并提示其中的金额、单位名称需人工复核
- 参考数据获取情况：比对用的标准模板文件与版本；模板未取到时写明哪些审查项因此未做
- 排版核对情况：合同正文的来源格式（PDF / docx），以及因来源格式而未能核对的项
```

## 写作要求

- 位置写条款号或小节标题，不写页码（PDF 抽取不保证页码准确）
- 原文用「」括起，只截取足以定位的片段
- 修改建议要给出可直接采用的表述方向，不写「建议完善」这种空话
- 同一问题不要在多个小节重复出现，选最贴切的一节写，其余小节引用其编号
